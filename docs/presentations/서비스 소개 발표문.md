# 컷노트(Cutnote) 프로젝트 종합 정리

> 영상 속 영감을 다음 작업에 꺼내 쓸 수 있도록 돕는, 장면 단위 영상 레퍼런스 관리 서비스.

- 작성 기준: 2026년 9월 29일 15:20 KST에 확인한 개발 대화·프로젝트 문서·핵심 소스.
- 용도: 팀 내부 정리, 랄프톤 발표, 시연 준비, VC 관점의 질의응답.
- 작성 관점: 우리는 발표자이며, 제품의 사용자 가치와 구현 근거를 설명한다.
- 확인 범위: 기존 검증 기록과 현재 소스를 검토했다. 이 문서 작성 과정에서 앱 실행·실기기 테스트·유료 AI 호출을 다시 수행하지는 않았다.

## 1. 프로젝트를 설명하는 기준 문장

| 구분 | 표현 |
|---|---|
| 서비스명 | 컷노트(Cutnote) |
| 한 문장 소개 | 영상 편집자가 저장한 영상의 색감·구도·효과와 참고 구간을 정리하고, 다음 작업에서 필요한 장면을 다시 찾도록 돕는 서비스입니다. |
| 사용자 문제 | 영상을 저장해도 어느 장면을 왜 참고하려 했는지 잊고, 제작을 시작할 때 여러 영상을 다시 확인해야 합니다. |
| 핵심 해결 방식 | 영상 링크·파일을 수집하고, AI가 제안한 태그와 시간 구간에 사용자의 메모를 연결합니다. |
| 제공 가치 | 저장 당시의 관심과 맥락을 남겨, 필요한 장면을 다시 찾고 활용하는 과정을 돕습니다. |
| 발표 핵심 문장 | 저희가 만드는 가치는 영상을 발견한 순간의 관심을, 다음 제작에서 활용할 수 있는 정보로 남기는 것입니다. |
| 마무리 문구 | 저장한 영감이 다음 작품으로 이어지는 곳, 컷노트입니다. |

### 출발점과 고객 가설

**확인된 출발점:** 영상편집 동아리 활동에서 인상적인 영상을 저장했지만, 이후 무엇 때문에 저장했는지 찾기 어려웠다는 팀의 경험이다. 아직 다수 고객을 대상으로 측정한 시장 검증 결과는 없다.

**초기 고객 제안:** 레퍼런스를 자주 수집하고 실제 제작에 반복적으로 사용하는 프리랜서 편집자와 소규모 제작팀.

**첫 검증 집단 제안:** 접근 가능한 영상편집 동아리 구성원과 편집자. 동아리는 문제를 관찰하고 제품을 시험할 출발점이며, 유료 고객군과 동일하다고 가정하지 않는다.

## 2. 사용자의 작업 흐름

```text
참고하고 싶은 영상 발견
  → 링크 또는 파일 등록
  → 분석 가능한 영상의 특징·효과·구간 제안
  → 사용자가 태그·시간·메모 확인 및 수정
  → 장면별 보관
  → 텍스트·태그·사진·효과로 검색
  → 원하는 구간 재생 및 참고
  → 검색 결과에 선택형 피드백
```

**설명용 예시 — 실제 고객 성과를 의미하지 않음**

1. 편집자가 영상의 12~15초 화면 전환을 참고하고 싶어 한다.
2. 해당 구간에 효과 태그와 “다음 동아리 홍보 영상 도입부에 참고”라는 메모를 붙인다.
3. 다음 제작에서 원하는 효과를 검색해 그 구간을 확인한다.
4. 추천된 다른 구간이 의도와 맞는지 선택형 피드백을 남긴다.

이 예시가 전달하는 가치는 **저장 → 정리 → 재발견 → 활용**이다. 실제 시간 절감과 반복 이용 효과는 앞으로 측정해야 한다.

## 3. 기능별 구현 상태와 발표용 표현

### 상태 표기

| 표기 | 의미 |
|---|---|
| 검증 기록 있음 | 개발 기록에 해당 기능의 실행 또는 저장·복구 확인이 남아 있다. 현재 모든 환경에서의 정상 동작을 보장한다는 뜻은 아니다. |
| 구현 확인 | 문서·소스에서 구현을 확인했다. 전체 사용자 흐름의 최신 검증은 별도로 필요하다. |
| 해결 확인 대기 | 사용자 오류 보고 또는 미검증 사항이 남아 있다. 완성·안정화를 선언하지 않는다. |
| 개발 요청 | 요구사항이 제시됐으나 완료 근거를 확인하지 못했다. |
| 제안 | 이 문서에서 제시하는 사업·제품 방향으로, 현재 기능이나 확정된 팀 결정이 아니다. |

## 4. 기술 구현을 설명하는 방법

### 4.1 구성

| 영역 | 확인한 구현 | 설명할 때의 핵심 |
|---|---|---|
| 웹 화면 | React·TypeScript, Tailwind 기반 UI | 수집·검색·구간 확인·검수를 한 흐름으로 연결 |
| 웹 실행·서버 | Next 호환 App Router 구조, vinext/Vite 실행, API routes | 화면과 분석·저장 API 연결 |
| 구조화 데이터 | Cloudflare D1, Drizzle, 구간·태그·분석 결과의 JSON 필드 | 영상과 장면의 특징·맥락·사용자 결정을 함께 보관 |
| 파일 저장 | Cloudflare R2 | 업로드 원본·썸네일·생성한 구간 파일 보관 |
| 영상 분석 | OpenAI 프레임 입력 경로, Gemini 영상 입력 경로 | 원본 접근 조건에 맞춰 분석하고 결과를 공통 구조로 검증 |
| 검색·추천 | 표준 태그·별칭·계층 관계·명시적 유사 효과 규칙 | 추천 이유를 설명할 수 있는 장면 탐색 |
| 사진 검색 | AI 특징 추출 후 구간 태그 일치·관련도 정렬 | 사진의 정적인 특징을 검색 조건으로 변환 |
| 구간 파일 생성 | Canvas·MediaRecorder·Web Audio 기반 브라우저 처리 | 원본에 접근할 수 있는 구간을 낮은 해상도로 보관 |
| Android | 공유 수신·WebView·파일 선택/저장 연결 | 휴대폰에서 PC 보관함을 사용하는 진입 경로 |
| PC 연결 | Node 기반 LAN 브리지와 페어링 인증 | PC의 기존 보관함·AI 설정을 앱에서 사용 |

### 4.2 AI가 하는 일과 애플리케이션이 하는 일

| AI가 담당 | 애플리케이션이 담당 | 사용자가 담당 |
|---|---|---|
| 영상·프레임에서 특징과 효과 후보 추출 | 허용된 태그 ID·형식·개수·시간 범위 검증 | 태그·시간 구간 확인과 수정 |
| 참고 구간·제목·메모 제안 | 영상·구간·메모·분석 근거 저장 | 개인적인 참고 이유 기록 |
| 자연어 검색을 태그 조건으로 해석 | 확정 태그와 유사 효과 규칙으로 검색·정렬 | 원하는 조건 선택과 추천 피드백 |
| 검색 사진의 정적 특징 추출 | 사진 특징과 저장된 구간의 태그 비교 | 결과를 실제 제작에서 활용할지 판단 |

**기술 발표용 표현:**

> AI가 영상의 특징과 검색 의도를 구조화하면, 컷노트가 이를 장면별 기록과 검색으로 연결합니다. 사용자는 근거 시점을 확인하고 태그와 메모를 수정할 수 있습니다.

### 4.3 분석 범위의 정확한 설명

- **OpenAI 경로:** 영상 전체 길이 또는 선택 구간에서 추출한 최대 120개 프레임을 분석한다. 음성은 제외하며 연속 재생·매 프레임 검사가 아니다. 영상 길이 한도는 2시간이다.
- **Gemini 경로:** 프로젝트 설정상 영상 입력과 2fps 샘플링을 사용한다. 공개 YouTube 또는 접근 가능한 원본을 대상으로 하며, 매 프레임 분석을 의미하지 않는다.
- **AI 점수:** 모델의 판단값이다. 예를 들어 0.85를 실측 정확도 85%로 설명하면 안 된다.
- **자동 확정 정책:** 관찰 가능한 태그의 점수가 0.85 이상이면 자동 확정하고, 0.60 이상인 나머지 후보는 검수 대상으로 남긴다. 제작·생성 방식처럼 추론이 필요한 항목은 점수와 무관하게 검수를 요구한다.
- **사진 검색:** 색감·구도·피사체·질감 등 정적인 특징을 활용한다. 사진 한 장으로 시간에 따른 움직임이나 편집 기법을 확인했다고 주장하지 않는다.

### 4.4 추천과 피드백의 실제 범위

1. 입력 문장을 AI 또는 로컬 규칙으로 태그 조건에 대응시킨다.
2. 현재 보관함의 **확정된 구간 태그**를 대상으로 검색한다.
3. 모든 조건이 맞는 구간과 일부 조건·유사 효과가 맞는 구간을 구분한다.
4. 조건 일치와 효과 가중치가 우선하며, 피드백은 같은 검색 조건에서 동률 우선순위 또는 숨김 처리 등에 반영된다.
5. 원본 태그를 피드백으로 자동 변경하지 않는다. 구간 내용이 바뀌면 이전 피드백의 적용 여부를 서명값으로 확인한다.

현재 근거로 설명할 수 있는 것은 **태그 기반 탐색과 검색 조건별 피드백 반영**이다. 별도의 개인화 모델 학습·파인튜닝·전체 YouTube 추천은 완료 기능으로 확인되지 않았다.

### 4.5 PC·앱·온라인 저장소 관계

```text
PC 로컬 웹 ────────────────┐
                          ├─ PC의 같은 보관함·AI 설정
Android 앱 → LAN 브리지 ───┘

온라인 배포 웹 ───────────── 별도 저장소·AI 설정
```

- 앱은 PC 서버에 접근하는 구조이며 독립 저장소를 복제하는 범용 동기화 서비스로 설명하지 않는다.
- 로컬 목록은 15초 주기 또는 화면 복귀 시 갱신하도록 구현되어 있다.
- 현재 방식에는 같은 Wi-Fi, PC와 연결 서버 실행이 필요하다.
- 온라인 웹과 PC 로컬 보관함의 자동 동기화는 지원 범위로 확인되지 않았다.
- 최신 사용자 보고에서 PC 내용이 앱에 보이지 않는 문제가 남아 있어 실제 연결은 재확인이 필요하다.

1. **PC–앱 연결:** 사용자가 원하는 보관함은 PC 로컬 보관함이다. 같은 클립이 실제 휴대폰에서 표시되고 변경이 반영되는지 확인한다.

3. **APK 0.4.1:** 빌드·서명·파일 검증과 실제 기기의 공유·재생·저장은 다른 검증 단계다.
4. **추천 범위:** 현재 보관함의 구간 추천과 새 YouTube 영상 추천을 구분한다.
5. **발표 수치:** 사용자 수·매출·정확도·시간 절감 수치는 아직 확인되지 않았다.

- **개인 이용:** 보관·검색·관리와 일정 분석 사용량을 묶는 구독 가설.

```text
고객별 월 기여이익 가설
  = 월 수입
  - 제품이 부담하는 AI 호출비
  - 저장·전송비
  - 결제·운영에 따른 변동비
```

시장 규모는 현재 수치가 없다. 초기 고객 범위·접근 가능한 고객 수·유료 전환율·가격을 각각 출처 또는 실험으로 뒷받침한 뒤 산정한다.

## 8. 필요한 검증과 성과 지표

아래는 성과가 아니라 **앞으로 실행할 검증안**이다.

| 확인할 질문 | 지표 정의 | 측정 방식 |
|---|---|---|
| 원하는 장면을 더 잘 찾는가? | 제한 시간 내 목표 구간을 찾은 비율 | 같은 난이도의 검색 과제로 기존 방식과 비교 |
| 더 빨리 찾는가? | 검색 시작부터 목표 구간 확인까지 걸린 시간 | 중앙값과 분포 비교. 실패 사례도 별도 기록 |
| AI 제안이 유용한가? | 그대로 승인·수정 후 승인·거절 비율 | 효과 유형과 영상 길이별로 구분 |
| 실제 다음 작업에서 쓰는가? | 나중에 다시 열어 참고한 저장 구간의 비율 | 다음 제작 시점에 재방문·활용 여부 확인 |
| 추천이 의도에 맞는가? | 상위 결과의 만족도와 선택형 피드백 분포 | 검색 유형별로 비교. 미응답을 긍정으로 간주하지 않음 |
| 비용을 지불하는가? | 명확한 유료 제안 후 실제 결제·유료 시범 이용 비율 | 가격·포함 범위·대상 고객을 고정해 실험 |
| 운영 가능한가? | 성공한 분석당 비용·소요 시간·실패율 | 제공자·길이·재시도 횟수별 기록 |
| 기기 연결이 안정적인가? | 공유→저장→PC 표시 흐름의 성공률 | 실제 휴대폰·네트워크별 확인 |

**초기 실험 제안:** 편집자 5~10명을 모집해 직접 저장한 영상으로 테스트한다. 이 인원은 검증 설계의 제안이며 기존 사용자 수가 아니다. 비교 과제는 순서를 교차하고 비슷한 난이도의 서로 다른 장면을 사용해 기억 효과를 줄인다. 인터뷰의 호감 표현과 실제 반복 이용·결제를 구분한다.

## 9. 발표 구성안

슬라이드가 필요할 때 사용할 7장 구성이다. 현재 PPT 파일을 제작했다는 의미는 아니다.

| 순서 | 슬라이드의 핵심 주장 | 보여줄 자료 | 말할 내용 |
|---|---|---|---|
| 1 | 저장한 영감을 다음 작품으로 연결한다 | 서비스명·대표 구간 카드 | 누구를 위한 어떤 제품인지 |
| 2 | 저장한 영상의 장면과 이유를 되찾기 어렵다 | 실제 동아리 경험과 작업 흐름 | 문제가 발생하는 구체적인 상황 |
| 3 | 수집부터 장면 검색까지 연결한다 | 링크→태그·구간→검색 화면 | 사용자의 행동이 어떻게 달라지는지 |
| 4 | 장면의 특징과 개인의 참고 맥락을 남긴다 | 근거 시점·메모·사진 검색·피드백 | 구현과 사용 가치가 연결되는 지점 |
| 5 | 반복 제작하는 고객부터 검증한다 | 초기 고객 가설·사용 장면 | 누가 먼저 필요로 하고 왜 반복 사용하는지 |
| 6 | 구독 가치와 운영 비용을 함께 확인한다 | 수익 가설·측정할 지표 | 과금·분석 원가·팀 확장 계획 |
| 7 | 핵심 흐름을 구현했고 반복 이용을 검증한다 | 구현 범위·남은 검증·마무리 문구 | 현재 성과와 다음 실행 계획 |

평가자에게 먼저 보여줄 것은 **장면을 다시 찾는 사용 경험**이다. 태그 수·API 이름·인프라 구성은 기능의 근거를 설명할 때 사용한다.

## 10. 발표문

### 10.1 짧은 소개문

안녕하세요. 저희는 영상 속 영감을 다음 작업에 꺼내 쓸 수 있도록 돕는 컷노트를 만들고 있습니다.

영상을 만들다 보면 좋은 색감이나 화면 전환을 발견해 저장합니다. 하지만 막상 작업을 시작하면 어떤 장면 때문에 저장했는지 다시 찾아야 합니다. 저희는 영상편집 동아리 활동에서 이 불편을 경험했습니다.

컷노트에서는 영상 링크나 파일을 추가하면 AI가 특징과 참고 구간을 제안합니다. 사용자는 태그와 시간을 확인하고, 자신이 참고하려던 이유를 메모로 남깁니다. 이후에는 텍스트·태그·사진으로 필요한 구간을 찾아볼 수 있습니다.

저희가 만들고 싶은 변화는 창작자가 장면을 다시 찾는 데 쓰는 시간을 줄이고, 자신의 작업에 어떻게 활용할지 고민하는 데 더 많은 시간을 쓰게 하는 것입니다.

저장한 영감이 다음 작품으로 이어지는 곳, 컷노트입니다. 감사합니다.

### 10.2 VC 관점을 반영한 발표문

안녕하세요. 저희는 영상 편집자가 저장한 레퍼런스를 실제 제작에 다시 활용하도록 돕는 컷노트를 만들고 있습니다.

저희가 주목한 문제는 영상 제작 과정에서 반복되는 레퍼런스 탐색과 정리 비용입니다.

편집자는 좋은 색감이나 화면 전환을 발견하면 영상을 저장합니다. 하지만 작업을 시작할 때는 그 영상이 어디에 있었는지, 몇 초의 어떤 장면을 참고하려 했는지 다시 찾아야 합니다. 저장한 자료가 늘어날수록 확인해야 하는 영상도 많아집니다.

이 문제는 저희의 영상편집 동아리 경험에서 출발했습니다. 초기 고객으로는 영상 제작이 잦은 프리랜서 편집자와 소규모 제작팀을 보고 있습니다. 레퍼런스를 찾고 활용하는 일이 자주 반복될수록, 이 과정을 돕는 도구의 가치도 커질 것이라는 가설입니다.

컷노트는 장면 단위의 기록과 검색으로 이 문제에 접근합니다.

사용자가 영상 링크나 파일을 추가하면, 분석 가능한 영상에서 AI가 색감·구도·효과와 관련 시간 구간을 제안합니다. 사용자는 결과를 확인하고 자신의 메모를 더합니다.

예를 들어 12초부터 15초 사이의 화면 전환에 “다음 홍보 영상의 도입부에 참고”라는 기록을 남길 수 있습니다. 이후 작업할 때는 원하는 효과를 검색해 해당 장면을 확인합니다. 말로 설명하기 어려운 느낌은 사진을 기준으로 찾아볼 수도 있습니다.

저희가 만드는 가치는 영상을 발견한 순간의 관심을, 다음 제작에서 활용할 수 있는 정보로 남기는 것입니다. 원본 영상, 참고 구간, 효과 태그, 개인 메모를 연결해 사용자가 그 장면에 주목했던 맥락까지 되찾도록 돕습니다.

효과 탐색에서는 저장된 구간 중 조건에 맞거나 유사한 장면을 보여줍니다. 사용자는 간단한 선택으로 피드백을 남길 수 있고, 그 선택은 같은 검색 조건의 결과에 반영됩니다. AI가 제안한 태그와 구간 역시 직접 수정할 수 있습니다.

사업 모델은 개인 구독에서 시작해 팀 이용으로 확장하는 방향을 검토하고 있습니다. 개인에게는 누적된 자료의 검색과 관리 가치를 제공하고, 향후 팀에는 프로젝트별 자료 공유와 공동 분류 기능을 제공하려 합니다. 동시에 분석 사용량과 저장 비용을 측정해 고객의 이용 가치와 운영 비용이 맞는지 확인하겠습니다.

현재는 수집, AI 분류, 구간별 기록, 사진·효과 검색과 선택형 피드백의 핵심 웹 기능을 구현했습니다. Android 공유와 PC 보관함 연결도 구현했으며, 실제 기기의 연결과 화면 안정성을 보완하고 있습니다.

다음 단계에서는 실제 편집 작업에서 필요한 장면을 찾는 시간이 줄어드는지, 저장한 자료를 다음 프로젝트에서도 다시 사용하는지, 그리고 그 가치에 비용을 지불할 의사가 있는지 검증하겠습니다.

장기적으로는 쌓인 참고 기록을 바탕으로 취향에 맞는 새로운 영상과 아직 시도하지 않은 스타일을 발견하도록 확장하고자 합니다.

저희는 컷노트를 영상 편집자가 작업을 시작할 때 자신의 참고 자료를 가장 먼저 찾아보는 공간으로 만들고 싶습니다.

저장한 영감이 다음 작품으로 이어지는 곳, 컷노트입니다. 감사합니다.

## 12. 예상 질문과 답변

**Q. 기존 저장 기능으로 충분하지 않나요?**

저희가 집중하는 작업은 저장한 영상에서 필요한 장면과 참고 이유를 다시 찾는 과정입니다. 컷노트는 시간 구간·태그·메모를 연결합니다. 이 연결이 실제 편집자의 반복 작업을 얼마나 개선하는지 검증하려 합니다.

**Q. AI가 틀리면 어떻게 하나요?**

근거 시점과 제안을 보여주고 사용자가 수정·승인·거절할 수 있습니다. 빠른 효과는 놓칠 수 있으므로 효과 유형별 오류를 측정하고, 사용자 수정 내용은 재분석 시에도 보호하도록 구현했습니다.

**Q. 추천 AI가 사용자의 취향을 학습하나요?**

현재는 저장된 구간의 확정 태그와 유사 효과 규칙으로 찾고, 같은 검색 조건의 피드백을 순서와 노출에 반영합니다. 누적 취향을 활용한 새 영상 추천은 추가 개발·검증 대상입니다.

**Q. 사진 검색은 무엇을 기준으로 하나요?**

사진에서 보이는 색감·구도·피사체·질감 등을 태그로 추출하고, 저장된 구간의 태그와 비교합니다. 시간에 따른 움직임을 사진 한 장으로 확인하는 기능으로 설명하지는 않습니다.

**Q. 모든 YouTube·Instagram 영상을 분석하거나 내려받을 수 있나요?**

플랫폼과 원본 접근 조건에 따라 다릅니다. 공개 YouTube 분석 경로와 파일 분석 경로를 두고 있고, 원본 접근이 어려우면 업로드를 안내합니다. YouTube 링크의 구간 파일 저장에는 같은 영상의 원본 첨부가 필요합니다.

**Q. 앱과 웹은 동기화되나요?**

현재 앱은 연결한 PC의 같은 보관함을 읽고 쓰는 구조입니다. 온라인 배포 사이트의 저장소는 별도입니다. 실제 PC–앱 연결 문제는 현재 보완 중입니다.

**Q. 누가 비용을 지불하나요?**

초기에는 레퍼런스 활용이 반복되는 편집자를 유료 고객 가설로 보고 있습니다. 실제 지불 의사와 이용 빈도를 확인한 뒤 개인 구독과 분석 사용량 구성을 정하려 합니다.

**Q. 외부 AI 모델을 쓰는데 제품의 경쟁력은 무엇인가요?**

저희가 구현한 부분은 분류 결과를 구간별 기록·검수·검색·피드백으로 이어주는 사용 흐름입니다. 이 흐름과 쌓인 참고 기록이 지속적인 이용 가치를 만드는지 검증해야 합니다. 현재 독점 기술이나 네트워크 효과를 확보했다고 주장하지 않습니다.

**Q. 어느 정도 성과를 냈나요?**

영상 분석·저장·구간 처리·검색의 검증 기록과 웹·APK 구현 결과가 있습니다. 아직 시장 성과로 제시할 사용자 수·매출·시간 절감 수치는 없습니다. 다음 검증은 실제 제작에서의 재사용과 지불 의사입니다.

**Q. 팀 서비스로 바로 판매할 수 있나요?**

현재는 소유자 중심 MVP입니다. 팀 이용에는 별도 계정·권한·공동 보관함·사용량 관리·과금 기능이 필요합니다.

## 13. 권장 우선순위

| 우선순위 | 할 일 | 필요한 이유 | 확인할 완료 기준 |
|---|---|---|---|
| P0 | PC–앱 연결 문제 해결 확인 | 사용자가 실제로 보고한 핵심 장애 | 실제 휴대폰에서 PC의 같은 영상·메모·즐겨찾기가 보이고 변경이 반영됨 |
| P0 | 화면 멈춤 재현·수정·재확인 | 시연과 반복 이용을 막을 수 있음 | 보고된 화면과 조작에서 오류가 재현되지 않고 주요 흐름을 마침 |
| P0 | 시연할 핵심 흐름 고정 | 구현 설명과 현장 동작 일치 | 수집→분석 또는 기존 결과→메모→검색→구간 재생을 연속 확인 |
| P1 | 실제 편집자의 탐색·재사용 테스트 | 기능 구현을 사용자 가치로 검증 | 과제 성공·탐색 시간·수정량·다음 작업 재사용 기록 확보 |
| P1 | 분석 원가·실패율 측정 | 과금 방식 결정의 근거 | 대표 길이별 성공·실패·재시도 비용과 대기 시간 확보 |
| P1 | 외부 YouTube 추천 범위 확정 | 기존 보관함 추천과 새 영상 발견 요구 구분 | 후보 수집 방법·추천 근거·스타일 확장 기준·피드백 범위를 문서화 |
| P2 | 단일 계정·보관함 경험 설계 | PC·온라인 저장소 혼동 감소 | 사용자에게 어느 보관함인지 명확하고 일관된 접근 구조 결정 |
| P2 | 공동 보관함·권한·과금 실험 | 팀 수요가 확인됐을 때 확장 | 역할·공유·접근 분리·사용량 책임을 정의하고 시범 이용 |

현재 가장 필요한 추가 작업은 **연결 안정화와 실제 반복 사용 검증**이다. 새 기능의 수보다 사용자가 저장한 장면을 다음 작업에서 다시 찾는 경험을 우선 확인한다.

### 외부 공개용으로 가져갈 때

- 발표문과 기능 소개에는 1·3·5·9·10절을 활용한다.
- 기술 질문에는 4절, 사업 질문에는 7·8·12절을 활용한다.
- 실제 상태가 바뀌면 3·6·13절의 상태와 검증 근거를 먼저 갱신한다.
- API 키·페어링 코드·서명 파일 등 개인 연결 정보는 이 문서에 포함하지 않았다.
- 시장 규모·경쟁사 우위·가격은 외부 조사와 고객 검증 전까지 확정 수치나 성과로 사용하지 않는다.
