문제를 여러 단계로 나누어 요구사항을 구체화하고, 단계별 구현을 위한 프롬프트를 생성해 Codex에 전달했다.

각 프롬프트에는 현재 프로젝트 상태, 참고 문서, 구현 목표, 수정 가능한 파일 범위, 이번 단계에서 제외할 기능을 명시했다. 이를 통해 작업 범위를 통제하고, 기존 구현이 의도와 다르게 변경되지 않도록 했다.

새로운 대화나 병렬 작업에서도 맥락이 이어지도록 프롬프트와 구현 결과를 마크다운으로 기록했다. 단계별 변경 사항, 버전 간 차이, 주요 규칙, 남은 작업을 정리해 다음 단계의 참고 자료로 활용했다.

기술과 구조를 선택할 때는 선택 이유와 대안별 차이를 질문하고, 결정 근거를 별도 문서로 남겼다. 제품 방향, MVP 요구사항, 기술적 결정을 구분해 관리했으며, MVC 구조에 따라 각 구성 요소의 책임과 상호작용 규칙을 명확히 정리했다.

각 단계의 완료 여부는 빌드, 린트, 테스트, 실제 실행 결과를 근거로 확인하도록 했다. 결과 보고에는 변경한 파일, 검증 항목별 성공·실패 여부, 실패 원인, 다음 단계로 진행할 수 있는지를 포함하도록 요청했다.

목표와 구현 범위가 충분히 구체화된 이후에는 완료 조건과 반복 작업의 종료 기준을 명시했다. 이를 바탕으로 Codex가 정해진 범위 안에서 구현·검증·오류 수정을 자율적으로 반복하도록 했다.

구현된 코드를 직접 이해하고 설명하기 위해 코드 구조 분석, 기술 개념 학습, UML 작성, 발표 자료 정리에도 Codex를 활용했다. 이 과정에서 요구사항과 판단 기준은 직접 정하고, 구현 결과를 검증·문서화하며 다음 작업으로 연결했다.
