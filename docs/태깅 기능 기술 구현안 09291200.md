이 서비스의 태깅은 단순히 AI에게 “이 영상에 무슨 효과가 있니?”라고 묻는 기능이 아니라, **정해진 태그 사전 안에서 클립을 다중 분류하고 사용자가 검수하는 시스템**으로 설계하는 것이 좋습니다.

현재 저장소에는 구현 코드가 없으므로, 아래는 MVP에 적합한 구체적인 설계안입니다.

## 1. 먼저 보완해야 할 태그 체계

현재 태그 사전에는 다음 8개 분류가 있습니다.

- Visual Style
- Generation Method
- Production Technique
- Transformation
- Motion Style
- Texture
- Geometry / Pattern
- Compositing

그런데 구현 범위 문서에는 `blue`, `warm`, `close-up`, `full-shot` 같은 **색감과 구도 태그**도 검색 조건으로 등장합니다. 현재 사전에는 이 두 영역이 빠져 있습니다.

따라서 최소한 다음 namespace를 추가하는 것이 좋습니다.

| 분류 | 예시 |
|---|---|
| `color` | blue, warm, desaturated, high-contrast |
| `shot_type` | close-up, medium-shot, full-shot, wide-shot |
| `camera_motion` | pan, tilt, dolly, handheld, orbit |
| `subject` | person, face, landscape, typography, product |

`Motion Style`은 화면 속 요소의 움직임, `Camera Motion`은 카메라 움직임으로 구분해야 검색 정확도가 높아집니다.

## 2. 태깅 결과의 구조

클립 하나에는 같은 분류의 태그도 여러 개 붙을 수 있습니다.

```json
{
  "clip_id": "clip_123",
  "taxonomy_version": "2026-09-01",
  "tags": [
    {
      "tag_id": "visual_style.digital_glitch",
      "score": 0.94,
      "source": "ai_observed",
      "status": "accepted",
      "evidence_ms": [500, 1500, 2500]
    },
    {
      "tag_id": "production_technique.rotoscoping",
      "score": 0.64,
      "source": "ai_inferred",
      "status": "suggested",
      "evidence_ms": [1500]
    },
    {
      "tag_id": "transformation.rgb_split",
      "score": 1.0,
      "source": "user",
      "status": "accepted",
      "evidence_ms": []
    }
  ]
}
```

여기서 특히 중요한 필드는 다음과 같습니다.

- `tag_id`: 표시 이름이 바뀌어도 유지되는 내부 ID
- `score`: AI가 계산한 분류 점수
- `source`: AI 관찰, AI 추정, 사용자 입력 구분
- `status`: 제안됨, 승인됨, 거절됨
- `evidence_ms`: 해당 효과가 관찰된 프레임 위치
- `taxonomy_version`: 어떤 버전의 태그 사전으로 분석했는지 표시

AI가 반환한 숫자를 곧바로 확률이나 신뢰도로 부르는 것은 피해야 합니다. 모델이 말한 `0.9`가 실제 90% 정확도를 의미하지 않기 때문입니다. 처음에는 `ai_score`로 저장하고, 검증 데이터가 쌓인 뒤 태그별 임계값을 보정해 `confidence`로 전환하는 편이 안전합니다.

## 3. 필요한 데이터베이스 구조

PostgreSQL 기준으로 다음 테이블이면 MVP를 구현할 수 있습니다.

### `tags`

태그 사전입니다.

```text
id
namespace
display_name
description
observable
parent_id
enabled
taxonomy_version
```

### `tag_aliases`

검색어를 표준 태그로 연결합니다.

```text
id
tag_id
alias
normalized_alias
language
```

예를 들어 `RGB Shift`, `Color Split`, `RGB Separation`을 모두 `transformation.rgb_split`으로 연결합니다.

### `tag_relations`

부모·자식 이외의 관계를 표현합니다.

```text
source_tag_id
target_tag_id
relation_type
```

`relation_type` 예:

- `parent_of`
- `related_to`
- `often_with`
- `conflicts_with`

### `clips`

```text
id
video_id
start_ms
end_ms
storage_path
thumbnail_path
duration_ms
analysis_status
created_by
```

시간은 부동소수점 초보다 정수형 밀리초로 저장하는 것이 좋습니다.

### `clip_tags`

```text
clip_id
tag_id
ai_score
source
status
created_by
analysis_run_id
created_at
updated_at
```

`clip_id + tag_id`를 유일 키로 두되, 사용자 승인 결과가 AI 재분석으로 덮어써지지 않게 해야 합니다.

### `tag_evidence`

```text
clip_tag_id
timestamp_ms
frame_path
evidence_type
```

### `analysis_runs`

```text
id
clip_id
model
prompt_version
taxonomy_version
status
raw_result
started_at
completed_at
error
```

이 테이블이 있어야 모델이나 프롬프트를 바꾼 뒤 결과를 비교하거나 재분석할 수 있습니다.

## 4. AI 태깅 파이프라인

전체 흐름은 다음과 같이 구성할 수 있습니다.

```text
클립 저장
  → 대표 프레임 추출
  → 프레임 묶음 생성
  → 시각 분석
  → 태그 ID 정규화
  → 점수·규칙 적용
  → 사용자 검수
  → 검색 인덱스 반영
```

### ① 대표 프레임 추출

FFmpeg로 클립에서 일정 간격의 프레임을 추출합니다.

- 3초 이하: 3~5장
- 3~10초: 초당 1장
- 긴 클립: 최대 12~16장
- 장면 전환 지점이 있으면 해당 프레임을 추가

FFmpeg는 시작 위치와 길이를 이용한 클립 생성과 인코딩을 지원합니다. [`-t`, `-to` 등 공식 문서](https://www.ffmpeg.org/ffmpeg.html)

비용 절감을 위해 개별 이미지를 전부 전송하기보다 여러 프레임을 하나의 contact sheet로 묶을 수도 있습니다.

### ② 분석을 두 종류로 분리

정지 프레임만으로 판단 가능한 태그:

- 색감
- 질감
- 구도
- 화면 스타일
- 형태와 패턴
- RGB Split, Blur 같은 일부 변형

시간 흐름을 봐야 하는 태그:

- Jitter
- Shake
- Zoom
- Stutter
- Slow Motion
- Morph
- Ghosting
- Camera Motion

따라서 모션 태그를 첫 프레임 하나로 판단하면 안 됩니다. MVP에서는 시간순 프레임 묶음을 전달하고, 이후에는 optical flow나 전용 비디오 모델을 추가할 수 있습니다.

### ③ 폐쇄형 태그 선택

AI가 새로운 태그 이름을 자유롭게 만드는 방식은 피해야 합니다. 요청에 현재 활성화된 태그 ID 목록과 정의를 전달하고, 그중에서만 선택하게 합니다.

```json
{
  "tags": [
    {
      "tag_id": "motion_style.jitter",
      "score": 0.84,
      "evidence_frame_indexes": [2, 3, 4]
    }
  ],
  "unclassified_observations": [
    "빠르게 번지는 빛 효과"
  ]
}
```

정해진 JSON Schema로 결과를 제한하면 파싱 오류를 줄일 수 있습니다. OpenAI Structured Outputs는 일반 JSON 모드와 달리 지정한 스키마 준수를 보장하도록 설계되어 있습니다. [Structured Outputs 공식 문서](https://developers.openai.com/api/docs/guides/structured-outputs)

이미지 입력 모델을 사용할 경우 여러 프레임을 순서대로 전달할 수 있습니다. [이미지·비전 입력 공식 문서](https://developers.openai.com/api/docs/guides/images-vision)

### ④ 규칙 및 임계값 적용

모든 태그에 같은 임계값을 사용하면 안 됩니다.

```text
score ≥ 자동 승인 임계값  → accepted
제안 임계값 ≤ score       → suggested
그 미만                   → 저장하지 않음
```

예:

```text
Digital Glitch: 자동 승인 0.85 / 제안 0.60
Rotoscoping: 자동 승인 없음 / 제안 0.70
```

`observable: false`인 제작 방식은 원본 프로젝트 파일 없이 확정하기 어려우므로 원칙적으로 자동 승인하지 않고 `AI 추정`으로만 보여주는 편이 좋습니다.

## 5. 사용자 검수 UI

AI 태깅은 완전 자동화보다 **검수 시간을 줄이는 보조 기능**으로 만드는 것이 현실적입니다.

클립 상세 화면에서 다음 기능이 필요합니다.

- AI 추천 태그 승인·거절
- 태그 검색 후 직접 추가
- 잘못 승인한 태그 제거
- 분류별 태그 묶음 표시
- 신뢰도가 낮은 태그 별도 표시
- 태그 근거 프레임 확인
- 유사어 입력 시 표준 태그 안내
- 사용자 피드백 저장

권장 표시 방식:

```text
확정 태그
[Digital Glitch] [RGB Split] [Jitter]

AI 제안
[VHS 71%]  승인 / 거절
[Rotoscoping · 추정]  승인 / 거절
```

사용자가 거절한 태그를 다음 AI 분석이 다시 붙이지 않도록 `rejected` 상태도 반드시 저장해야 합니다.

## 6. 검색 구현

MVP 검색은 벡터 검색보다 **관계형 필터 검색을 우선**해야 합니다.

예를 들어:

```text
Digital Glitch AND Blue AND Fast
```

는 `clip_tags`를 태그별로 조인하거나, `GROUP BY clip_id HAVING COUNT(DISTINCT tag_id) = 3` 형태로 정확하게 검색할 수 있습니다.

검색 기능은 다음 순서로 구현하면 됩니다.

1. 정확한 태그 필터
2. alias 기반 문자열 검색
3. 부모 태그 검색 시 하위 태그 포함
4. AND/OR 조합
5. 신뢰도와 사용자 확정 여부 필터
6. 유사 클립 검색

벡터 검색은 “이 클립과 비슷한 분위기” 또는 자연어 검색에 유용한 확장 기능입니다. PostgreSQL의 pgvector는 코사인 거리와 HNSW/IVFFlat 인덱스를 지원하므로 별도 벡터 데이터베이스 없이 확장할 수 있습니다. [pgvector 공식 저장소](https://github.com/pgvector/pgvector)

단, 태그 필터 자체를 처음부터 벡터 검색으로 구현할 필요는 없습니다. 정확한 태그 조합은 일반 SQL이 더 예측 가능합니다.

## 7. 추천 기술 구성

MVP라면 다음 조합이 구현 난이도와 확장성의 균형이 좋습니다.

| 영역 | 권장 기술 |
|---|---|
| 웹 UI | Next.js + TypeScript |
| API | Next.js API 또는 FastAPI |
| 영상 처리 | FFmpeg |
| 비동기 작업 | Redis + BullMQ 또는 Python 작업 큐 |
| DB | PostgreSQL |
| 파일 저장 | S3 또는 Supabase Storage |
| 인증 | Supabase Auth |
| AI 분석 | 멀티모달 모델 + Structured Outputs |
| 유사도 검색 | pgvector, MVP 이후 |
| 배포 | Vercel + 별도 영상 처리 Worker |

영상 처리와 AI 분석은 요청 시간이 길기 때문에 일반 HTTP 요청 안에서 완료하려 하면 안 됩니다.

```text
POST /clips/{id}/analyze
  → 작업 생성
  → 즉시 job_id 반환
  → Worker가 FFmpeg와 AI 분석 실행
  → UI가 상태 조회 또는 실시간 알림 수신
```

분석 상태는 다음처럼 관리합니다.

```text
pending → extracting_frames → analyzing → review_required → completed
                                              ↘ failed
```

## 8. MVP 구현 우선순위

행사나 프로토타입 기준으로는 아래 범위가 적절합니다.

### 반드시 구현

- 표준 태그 seed 데이터
- 태그·별칭·클립 태그 DB
- 사용자 수동 태그 추가·삭제
- 카테고리별 복수 태그
- 태그 조합 검색
- AI 분석 작업 상태
- 대표 프레임 기반 태그 추천
- 추천 승인·거절

### 시간 여유가 있으면 구현

- 태그별 점수와 근거 프레임
- 부모·자식 태그 검색
- 클립 재분석
- 자연어 검색
- 유사 클립 추천
- 자동 임계값 보정

### MVP 이후

- 실제 동영상 전용 모델
- optical flow 기반 모션 분석
- 사용자 피드백을 이용한 분류기 학습
- 외부 영상 자동 탐색
- 태그 품질 모니터링과 모델 평가

## 9. 구현 전에 정해야 할 정책

기술보다 먼저 다음 규칙을 확정해야 합니다.

- 부모 태그를 자동으로 함께 저장할지, 검색할 때만 확장할지
- 사용자 태그가 AI 분석보다 항상 우선하는지
- AI 재분석 시 기존 결과를 교체할지 이력으로 남길지
- 클립당 같은 분류의 최대 태그 수
- 서로 모순되는 태그 처리 방식
- 태그 사전 버전 변경 시 과거 클립을 재분석할지
- 자동 승인 가능한 태그와 제안만 가능한 태그 구분

가장 현실적인 첫 구현은 **“프레임 기반 AI 후보 생성 + 사용자 승인 + 정확한 태그 필터 검색”**입니다. 이 구조만으로도 서비스의 핵심 가치를 검증할 수 있고, 이후 모션 분석과 유사도 검색을 자연스럽게 추가할 수 있습니다.
